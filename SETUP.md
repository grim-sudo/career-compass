# Local setup guide

## 1. Prerequisites

- Docker Engine or Docker Desktop, running, with Docker Compose v2.
- Node.js 22 or newer and npm for the setup helper.
- A Gemini, OpenAI or Anthropic (Claude) API key with access to the configured model.
- Port 3000 available. Stop any previous Career Compass dev servers first.

Run all commands from the repository root. Docker builds and serves the app;
do not run `npm start` alongside it on the same ports.

## 2. Configure

```bash
npm run setup:local
```

The helper creates missing files and preserves existing settings:

| File | Setting | Meaning |
|---|---|---|
| `.env` | `POSTGRES_PASSWORD` | Random database credential generated by setup |
| `.env` | `APP_PORT=3000` | Published browser port |
| `backend/.env` | `AI_PROVIDER=gemini` | Select `gemini`, `openai` or `claude` |
| `backend/.env` | `GEMINI_API_KEY`, `OPENAI_API_KEY` or `ANTHROPIC_API_KEY` | Key for the selected provider |
| `backend/.env` | `GEMINI_MODEL`, `OPENAI_MODEL` or `CLAUDE_MODEL` | Optional model selection; defaults listed in README |

Edit `backend/.env` and replace the example key if needed. Never put a key in
frontend code or a `REACT_APP_*` variable. No frontend env file is required.
Both real env files are Git-ignored and excluded from the Docker build context.

The database password is 48 hexadecimal characters generated from 24 random
bytes, not an account password. Its format avoids URL-escaping issues. Retain
the root `.env` with the database volume: changing `POSTGRES_PASSWORD` later does
not update the existing database role. Password rotation requires a coordinated
PostgreSQL role change and app recreation, not deleting the volume.

Compose supplies `DATABASE_URL`, the internal listening address, allowed browser
origins, and local cookie settings. AI configuration stays in the backend
file and is injected at runtime, not compiled into the frontend.

## 3. Start and verify

```bash
npm run start:local
docker compose ps
curl --fail http://localhost:3000/api/health
```

Both `app` and `db` should be **healthy**. Health returns `ok`,
`databaseAvailable`, `aiProvider`, `aiConfigured` and legacy `geminiConfigured`;
flags check configuration, not provider availability. Open http://localhost:3000,
create a local account and send a career question to verify a real provider reply.

For subsequent starts, reuse `npm run start:local`. After backend env changes:

```bash
docker compose up -d --force-recreate app --wait
```

A restart alone does not reload a container's environment. Source changes require
`npm run start:local` to rebuild. The app port binds only to `127.0.0.1`; PostgreSQL
is reachable only inside the Compose network.

## 4. Stop without losing data

```bash
npm run stop:local
```

The named volume `career-compass_postgres_data` retains accounts and histories
across down/up, restart, and rebuild. Keep tabs open until **Saved locally** appears.
If a stale-tab conflict occurs, copy unsaved text before reloading.

**`docker compose down -v` permanently deletes the database volume.** It is not
a normal shutdown or a fix for a connection error.

## Troubleshooting

| Symptom | Check |
|---|---|
| Docker connection failure | Start the daemon/Desktop; verify `docker info` works |
| Port already allocated | Stop the old server or change `APP_PORT` in root `.env`, then recreate the app |
| App restarting, database healthy | Inspect `docker compose logs --tail=100 app`; check credentials and network membership |
| Browser requests `localhost:5000` / CORS error | It is running stale frontend code. Stop the old dev server, rebuild Compose, then hard-refresh |
| Session connection error | Check health at the same browser origin and confirm both services are healthy |
| AI unavailable | Check `AI_PROVIDER` and its key in `backend/.env`, recreate the app, and check model access/billing/quota |

Docker browser requests should target `/api` on the **same port as the page**.
Use either `localhost` or `127.0.0.1` consistently; session cookies are host-specific.
CORS remains allowlisted and credential-aware; do not disable browser security
or add a wildcard origin to work around stale servers.

## Backups and recovery

Save backups outside the repository. They contain private account/chat data,
password hashes, and session records; protect access and choose your own retention.

```bash
mkdir -p "$HOME/career-compass-backups"
docker compose exec -T db pg_dump -U career -d career_compass -Fc > "$HOME/career-compass-backups/career-compass.dump"
docker compose exec -T db pg_restore --list < "$HOME/career-compass-backups/career-compass.dump"
```

Test a backup in a separate, newly created database:

```bash
docker compose exec -T db createdb -U career career_compass_restore
docker compose exec -T db pg_restore --single-transaction --exit-on-error --no-owner -U career -d career_compass_restore < "$HOME/career-compass-backups/career-compass.dump"
```

Inspect the restored data before trusting recovery. Do not overwrite live data.
For actual recovery, stop the app and restore into a confirmed empty
`career_compass` database using the same restore options, then restart the app.
Keep a current backup before any destructive database operation.

## Native development (optional)

Use this instead of the full Docker app when editing with hot reload. It requires
a separate, already running local PostgreSQL instance; Compose's database has
no host port.

```bash
npm ci --ignore-scripts --no-audit --no-fund
npm run install-all
```

Set `DATABASE_URL` in `backend/.env` to your local database. Keep `HOST=127.0.0.1`,
`PORT=5000`, and `FRONTEND_ORIGIN=http://localhost:3000`. Then run `npm start`.
CRA proxies same-origin `/api` requests to port 5000. No frontend API URL is used.

```bash
npm test --prefix backend
TEST_DATABASE_URL=postgresql://user:password@127.0.0.1:5432/career_compass_test npm run test:local --prefix backend
CI=true npm test --prefix frontend -- --watchAll=false --runInBand
node frontend/scripts/start.test.cjs
npm run build
docker compose config --quiet
```

Database tests initialize tables and delete only the accounts they create. Always
point them at an isolated test database. Local storage does not make AI
offline; provider usage may incur charges under your API account.
